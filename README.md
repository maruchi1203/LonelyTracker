# LonelyTracker

> 자기개발 기록을 위한 일정 관리 웹앱

## 만든 이유

1. 스케줄 앱 **TickTick**을 사용하며 예정된 일과 할 일을 일일히 정리하는 게 귀찮았다.
2. Claude나 GPT 같은 AI를 사용할 일이 많은데 일정도 AI가 정리해주면 좋겠다 싶었다.
3. **ReclaimAI** 같은 서비스 이용해도 되긴 하는데, 난 AI가 평일 기록들을 보고 주말에 뭐할지, 시간날 때 뭐 공부하면 좋을지 일정 추천도 해주면 좋겠다 싶었다.

---

## 달력 앱과 무엇이 다른가

만들면서 방향이 분명해졌다. **일정 관리 도구가 아니라 습관 형성 도구다.**

목표 기록을 네 칸으로 구성한다. 2분 법칙(*Atomic Habits*)과 실행 의도(implementation intention)를 따른 것이다.

| 칸 | 내용 |
| --- | --- |
| 목표 | 이루고 싶은 것 |
| 행동 | 목표 달성을 위해 해야 할 구체적 행동 |
| 시간/장소 | 언제, 어디서. **구체적일수록 성공 확률이 높다** |
| 2분 행동 | 시작에 필요한 2분 이내 미니 행동 (`"헬스장 가기"` → `"퇴근 후 운동복 갈아입기"`) |

이 기준이 기능 판단에도 쓰인다. *"달력 앱에 있나"* 가 아니라 ***"이 네 칸을 채우는 데 도움이 되나"*** 로 정한다.

그래서 이런 것들이 나왔다.

- **연기와 건너뛰기를 구분한다** — 미룬 사람과 그만둔 사람은 다르다
- **미룬 횟수를 센다** — 수행률만 보면 두 사람이 같아 보인다
- **AI가 되묻는다** — 장소가 비었거나 행동이 막연하면 채우도록 질문한다

## 설계에서 신경 쓴 것

### 반복 일정을 행으로 만들지 않는다

`"매일 독서"` 를 1년치 행으로 미리 만들면 366행이 생긴다. 그렇게 하지 않았다.

```
schedule           일정의 정체     무엇인가
schedule_recur     반복 규칙       언제 반복되나 (행이 없으면 1회성)
schedule_progress  회차별 수행     어떻게 됐나 (행이 없으면 PLANNED)
```

회차는 **조회할 때 규칙에서 펼친다.** 손댄 회차만 기록이 남는다.

미리 만드는 방식보다 저장량이 적은 것도 있지만, 더 큰 이유는 **"아직 일어나지 않은 일"을 데이터로 확정하지 않는다**는 것이다. 덕분에 이런 것들이 한 줄로 끝난다.

| 동작 | 하는 일 |
| --- | --- |
| 요일 변경 | 규칙 `UPDATE` 1행 — 재생성이 필요 없다 |
| 그만두기 | 종료일을 오늘로 당기는 `UPDATE` 1행 — 지난 기록은 남는다 |
| 무기한 반복 | 그냥 종료일이 `null` — 상한이 필요 없다 |

대가도 있다. 수행률의 분모, 시각 기준 조회, 정렬은 **SQL 한 방으로 안 나오고** 전개를 거쳐야 한다.

### 연기는 상태가 아니라 두 날짜다

```
progress(onDate = 8/25, startAt = 8/26 07:00, postponeCount = 1)
         ─────────────  ────────────────────
         계획했던 날      실제로 간 날
```

한 행이 두 날짜를 동시에 갖는다. `onDate`가 회차의 정체성이라 미뤄도 **원래 날짜가 사라지지 않는다.** 세 번 미뤄도 행은 하나고 `postponeCount`가 3이 된다.

이 값이 코칭의 발동 조건이다.

```
운동   수행률 92%  ·  미룸 14회     ← 하긴 하는데 항상 밀린다
독서   수행률 91%  ·  미룸  0회     ← 계획대로 한다
```

**수행률만 보면 둘이 같은 사람이다.**

### AI를 믿지 않는 구조

```
POST /api/schedules/parse   →  초안 반환 (저장하지 않음)
사용자가 화면에서 확인·수정
POST /api/schedules         →  기존 생성 API 재사용
```

- **`ScheduleParser` 인터페이스가 유일한 LLM 경계다.** 제공자 교체가 아니라 테스트를 위한 것이다. API를 한 번도 부르지 않고 검증·실패 처리·저장 흐름을 전부 테스트한다
- **`now`를 인자로 받는다.** 안에서 `LocalDateTime.now()`를 부르면 `"내일 3시"` 해석을 테스트할 방법이 없다
- **파싱 서비스에 `@Transactional`이 없는 것이 설계다.** LLM은 수 초가 걸리는데 트랜잭션 안에서 부르면 그동안 DB 커넥션을 잡는다. 커넥션 풀이 10개면 동시에 열 명이 앱을 멈춘다
- **응답을 사용자 입력과 같은 등급으로 검증한다.** 목록에 없는 분류를 지어내면 버린다
- **모르는 값은 지어내지 않고 되묻는다.** 모델은 질문 ID만 고르고 문구는 서버가 갖는다 — JSON 스키마에 `enum`으로 걸어 질문을 만들어낼 수 없게 했다
- 읽기 타임아웃을 건다. 기본값이 무한 대기다
- **4xx는 재시도하지 않는다.** 몇 번을 보내도 같은 결과다

### API 키는 서버가 아니라 사용자가 갖는다

키를 `.env`에 두면 **서버가 모든 사용자의 사용료를 대신 내게 된다.** 사용량도 쓰는 사람에게 귀속되지 않는다. 그래서 사용자별로 저장한다.

DB 접속 정보는 반대다. 서버가 **하나의 DB**를 쓰므로 서버 설정에 남는다. *"사용자마다 다른가"* 가 기준이다.

키는 비밀번호와 같은 등급이라 이렇게 다룬다.

- **AES-GCM으로 암호화해 저장** — 암호화와 무결성 검증을 함께 한다. 저장값이 조작되면 복호화가 실패한다
- **IV를 값마다 새로 만든다** — 안 그러면 같은 평문이 항상 같은 암호문이 되어 *"이 두 사용자는 같은 키를 쓴다"* 가 DB만 보고도 드러난다
- **어떤 응답에도 원본을 싣지 않는다** — 등록 여부와 끝 네 자리(`****1234`)만 보여준다
- 마스터 키는 환경변수로 받는다. 없으면 앱은 뜨되 키 저장만 막힌다

Spring AI를 쓰지 않은 이유는, **타임아웃·재시도·검증을 어떻게 설계했는지가 이 프로젝트에서 보여줄 판단**이기 때문이다. 프레임워크에 맡기면 그 판단이 코드에 남지 않는다.

### 권한 없는 접근은 403이 아니라 404

```java
scheduleRepository.findById(id)
        .filter(s -> s.getUser().getId().equals(userId))
        .orElseThrow(() -> new NotFoundException(...));
```

403은 *"그 id는 존재하지만 네 것이 아니다"* 를 알려준다. 남의 데이터 존재 여부가 새므로 404로 통일했다.

### 분류는 FK가 아니라 문자열

목록에서 분류를 지우거나 이름을 바꿔도 **이미 기록한 일정의 분류는 그대로여야 한다.** 정규화보다 기록 보존이 중요한 경우다. 이 의도를 테스트로 못 박아 뒀다.

## 겪은 문제와 해결

### `ddl-auto: update`는 컬럼을 지우지 않는다

엔티티에서 필드를 삭제했는데 DB 컬럼이 `NOT NULL`로 남아 **모든 INSERT가 실패**했다. `update`는 이름 그대로 추가만 한다.
→ Flyway 도입. `ddl-auto`는 `validate`로 내려 스키마를 고치는 주체를 하나로 통일했다.

### 라이브러리는 넣었는데 아무 일도 일어나지 않았다

`flyway-core`만 넣고 Spring Boot 4의 자동설정 모듈(`spring-boot-flyway`)을 빠뜨렸다.
→ jar 안의 `AutoConfiguration.imports` 등록부를 직접 열어 확인하고 해결. **검색 결과보다 실제 아티팩트를 여는 게 빠르다**는 걸 배웠다.

### `ON DELETE CASCADE`가 있는데 삭제가 터졌다

DB에 제약을 걸어뒀는데 `TransientPropertyValueException`이 났다.

```
DB:        "부모를 지우면 자식도 지운다"          ← SQL 실행 시점
Hibernate: "자식이 없어진 부모를 가리킨다" → 거부  ← flush 시점 (더 앞)
```

**검사 지점이 다르다.** Hibernate는 SQL을 보내기 전에 메모리 안의 객체 그래프를 본다.

| 시도 | 결과 |
| --- | --- |
| `@OnDelete(CASCADE)` | ❌ DDL 생성용이라 영속성 컨텍스트를 안 건드린다 |
| 벌크 `@Modifying @Query` | ❌ DB만 바꾸고 컨텍스트는 그대로 |
| 파생 삭제 `deleteByScheduleId()` | ✅ 로드 후 remove → 컨텍스트까지 정리 |

세 결과가 **"영속성 컨텍스트를 정리하는가"** 한 가지로 설명된다.

### JVM 크래시 11건 — 우회 설정이 힙 상한을 지웠다

프로젝트 경로에 한글이 있어 `org.gradle.jvmargs`로 인코딩을 지정했는데, 이 설정이 Gradle 기본 JVM 옵션을 **대체**한다는 걸 몰랐다. 힙 상한이 사라져 JVM 기본값(물리 메모리의 1/4 = 8.5GB)이 적용됐고, 빌드마다 뜨는 JVM이 그만큼씩 예약하며 메모리가 고갈됐다.
→ 힙 상한 명시. 근본 원인인 한글 경로를 없애니 우회 설정 자체가 필요 없어졌다.

### 설계를 두 번 뒤집었다

반복 일정 저장 구조를 **미리 생성 → (날짜 문자열 검토·폐기) → 규칙 + 기록**으로 바꿨다.

```
습관 1개 · 1년 · 90% 체크

  미리 생성       366행 ≈ 110 KB
  규칙 + 기록     331행 ≈  36 KB
  날짜 문자열       1행 ≈   4 KB
```

문자열이 25배 작지만 폐기했다. **수행률 집계가 SQL에서 안 나오고, 연기의 대상 시각을 담을 자리가 없고, 컬럼이 무한히 자라고, 체크 한 번이 원자적이지 않다.** "작다"는 여러 기준 중 하나일 뿐이다.

되돌아보면 **프론트엔드를 쓰기 전에 뒤집은 것**이 다행이었다. 최대 소비자가 없을 때가 가장 싼 시점이다.

## 실행

`backend/.env` 에 DB 접속 정보를 넣는다.

```properties
DB_URL=jdbc:postgresql://localhost:5432/lonelytracker
DB_USERNAME=lonelytracker
DB_PASSWORD=
```

```bash
# 백엔드
cd backend && ./gradlew bootRun

# 프론트엔드
cd frontend && npm install && npm run dev
```

테스트는 **Docker가 떠 있어야 한다.** Testcontainers가 PostgreSQL 컨테이너를 띄운다.

```bash
cd backend && ./gradlew test
```

AI를 쓰려면 **사용자가 자기 OpenAI 키를 등록**한다.

```
PUT /api/users/me/openai-key   {"apiKey": "sk-..."}
```

키를 암호화해 저장하려면 서버에 마스터 키가 필요하다. 이건 **서버의 것**이라 환경변수로 준다.

```properties
LONELYTRACKER_ENCRYPTION_KEY=아무_긴_문자열
```
