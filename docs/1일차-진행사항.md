## 3. 백엔드 (최종)

### 도메인

**Schedule**

| 필드 | 타입 | 비고 |
|---|---|---|
| `title` | String(200) | 필수 |
| `description` | TEXT | **마크다운 원문**. 렌더링은 화면 담당 |
| `startAt` / `endAt` | LocalDateTime | endAt은 선택 |
| `allDay` | boolean | |
| `status` | enum | PLANNED / DONE / SKIPPED |
| `category` | ManyToOne | LAZY, nullable(미분류 허용) |
| `createdAt` / `updatedAt` | LocalDateTime | JPA 감사 |

**Category** — 계층은 `parent_id`로 잡되 전체 경로 `path`를 함께 보관한다.

| 필드 | 비고 |
|---|---|
| `name` | 마지막 세그먼트만 (`능력\개발` → `개발`) |
| `parent` | 자기참조 |
| `path` | 루트부터의 전체 경로, unique |
| `displayOrder` / `color` / `collapsed` / `archived` | 사이드바 표시용 |

`path`를 중복 보관하는 대가로 **"하위 포함 필터"가 재귀 조회 없이 prefix 비교 한 번**으로 끝난다.
반대급부는 이름 변경 시 후손의 `path`도 갱신해야 한다는 점이고, `CategoryService.rename()`이 담당한다.

### 엔드포인트

**일정** `/api/schedules`

| 메서드 | 경로 | 응답 |
|---|---|---|
| GET | `?from=&to=&status=&category=` | 200 |
| GET | `/{id}` | 200 / 404 |
| POST | | 201 + Location |
| PUT | `/{id}` | 200 / 404 |
| PATCH | `/{id}/status` | 200 / 404 |
| DELETE | `/{id}` | 204 / 404 |

`category`는 **하위까지 포함**해 조회한다. `능력` → `능력\개발`은 걸리고 `능력강화`는 안 걸린다.
생성·수정 시 `categoryPath` 문자열을 받아 **없으면 중간 단계까지 만들어 붙인다**(get-or-create).

**카테고리** `/api/categories`

| 메서드 | 경로 | 비고 |
|---|---|---|
| GET | | 경로순 (부모가 자식보다 먼저) |
| POST | | 중간 단계 없으면 함께 생성 |
| PATCH | `/{id}/name` | 후손 경로 자동 갱신 |
| PATCH | `/{id}/appearance` | 색상·순서·접힘·보관 |
| DELETE | `/{id}` | 하위 있으면 400, 일정은 미분류로 남김 |

### 설계상 지킨 것

- **엔티티를 직접 반환하지 않는다.** DTO로 변환한다. `open-in-view: false` 환경에서
  지연 로딩이 직렬화 중 터지는 것을 막고, 엔티티 변경이 API 계약에 새지 않게 한다.
- **setter 대신 의도가 드러나는 메서드.** `update()`, `changeStatus()`, `rename()`만 열어둔다.
- **예외는 `@RestControllerAdvice`에서 일괄 변환.** 컨트롤러에 try-catch가 없다.
- **조회는 Specification(동적 쿼리).** 조건이 있을 때만 predicate를 붙인다.

## 5. 스키마 관리 — Flyway

`ddl-auto: update`는 컬럼 추가만 하고 **삭제와 타입 변경을 하지 않는다.**
실제로 `source` 필드를 지웠을 때 DB 컬럼이 NOT NULL로 남아 모든 INSERT가 실패했다.
스키마를 고치는 주체를 Flyway 하나로 통일하고 `ddl-auto`는 `validate`로 내렸다.

| 파일 | 내용 |
|---|---|
| `V1__init.sql` | 기존 스키마 베이스라인. 기존 DB에서는 기록만 되고 실행되지 않는다 |
| `V2__drop_source_and_widen_columns.sql` | source 제거, description → TEXT, category 확장 |
| `V3__add_category_table.sql` | category 테이블 생성 + 기존 문자열 이관 + FK 연결 |

실행 로그가 설계 그대로 나왔다.

```
Successfully baselined schema with version: 1
Migrating schema "public" to version "2 - drop source and widen columns"
Migrating schema "public" to version "3 - add category table"
```

**규칙: 이미 적용된 마이그레이션 파일은 수정 금지.** checksum이 어긋나면 앱이 기동을 거부한다.
변경이 필요하면 새 버전을 추가한다.

**V3의 데이터 이관** — `능력\개발\SpringBoot` 문자열 하나에서 상위 경로 3개를 모두 만들어야
계층이 완성되므로, `generate_series`로 경로 접두사를 펼쳐 넣고 `parent_id`를 연결했다.
테이블 생성·데이터 이관·FK 연결이 **한 파일에서 원자적으로** 처리된다 — `ddl-auto`로는 불가능한 부분.

## 6. 검증 결과

**API** — 일정 6개, 카테고리 5개 엔드포인트 동작 확인.

**에러 처리** — 모두 통일된 JSON으로 응답:

| 상황 | 코드 |
|---|---|
| title 누락 / endAt < startAt / 깨진 JSON / 잘못된 enum | 400 |
| 하위 있는 카테고리 삭제 | 400 + 안내 메시지 |
| 없는 id | 404 |

**카테고리 계층**

- 기존 문자열 4종 → 카테고리 7개로 이관, 부모 연결까지 정확
- 하위 포함 필터: `능력` 4건 / `능력\개발` 2건 / `취미` 1건 / `능력강화` 0건
- **이름 변경 `능력\개발` → `능력\학습` 한 번에 후손 2개 경로가 갱신되고 일정도 그대로 따라왔다.**
  FK 참조라 일정 테이블은 건드릴 필요가 없다 — 엔티티 승격의 실익이 확인된 지점
- 화면에서 `능력\개발\DB\Flyway` 입력 → `DB`, `Flyway` 두 단계가 자동 생성되어 사이드바에 반영

**기타**

- 마크다운 원문(백틱·체크박스·인용문 포함) 왕복 일치
- LIKE 와일드카드(`%`) 주입 시 리터럴 처리
- 브라우저에서 등록·정렬·상태토글·삭제·필터 동작 확인, 콘솔 에러 없음
- 백엔드 `gradlew build`(테스트 포함), 프론트 `npm run build`(타입 검사 포함) 성공

## 7. 구현 중 해결한 문제

오늘 가장 시간이 든 부분이자 재발 가능성이 있는 항목들.

### ① 한글 경로 때문에 테스트가 실행조차 안 됨

프로젝트 경로에 `바탕 화면`이 포함돼, Gradle이 UTF-8로 쓴 테스트 워커 `@argfile`을
Java 런처가 시스템 인코딩(CP949)으로 읽어 클래스패스가 깨졌다.
증상은 `ClassNotFoundException`인데 클래스 파일은 멀쩡히 존재하는 형태.

→ `gradle.properties`에 `org.gradle.jvmargs=-Dfile.encoding=MS949`로 해결.

**근본 대책은 프로젝트를 ASCII 경로로 옮기는 것.** OneDrive가 `node_modules`
수만 개 파일을 동기화하며 빌드 중 파일 잠금을 일으키는 문제도 함께 사라진다.

### ② Spring Boot는 `.env`를 자동으로 읽지 않는다

`.env`는 Node/Docker 관례라 `${DB_PASSWORD}`는 OS 환경변수만 찾는다.

→ `spring.config.import: optional:file:.env[.properties]` 로 해결.
`optional:`을 붙였으므로 `.env`가 없는 배포 환경에서도 앱은 정상 기동한다.

### ③ `:param is null` 패턴이 PostgreSQL에서 실패

기간·상태 조회를 JPQL `(:from is null or s.startAt >= :from)`로 짰더니
`$1 매개 변수의 자료형을 알수가 없습니다` 오류. PostgreSQL은 null 비교에만 쓰인
파라미터의 타입을 추론하지 못한다.

→ **Specification(동적 쿼리)** 으로 교체. 조건이 있을 때만 predicate를 붙이므로
생성되는 SQL도 더 깔끔하다.

### ④ 원시 `boolean`은 JSON 선택 필드로 쓸 수 없다

`allDay`를 생략하고 POST하면 `Cannot map null into type boolean`.

→ 요청 DTO에서 `Boolean` 래퍼를 쓰고 서비스에서 null을 false로 취급.

### ⑤ `updatedAt`이 갱신 전 값으로 응답됨

`@LastModifiedDate`는 flush 시점에 채워진다. 변경 감지만 믿고 바로 DTO를 만들면
응답에는 수정 전 `updatedAt`이 실린다.

→ 수정·상태변경 시 `saveAndFlush` 후 응답 생성.

### ⑥ 스택트레이스가 API 응답에 노출됨

에러 응답에 자바 스택트레이스가 통째로 실려 나왔다. devtools가
`include-stacktrace=always`를 기본으로 심기 때문.

→ `spring.devtools.add-properties: false`로 차단.

추가로 **Boot 4에서 `server.error.include-stacktrace`는 error 레벨로 폐기**되고
`spring.web.error.include-stacktrace`로 옮겨졌다. 3.x 기준 자료를 보고 옛 이름을 쓰면
조용히 무시된다.

### ⑦ YAML Map 키 이스케이프

`logging.level`과 `spring.jpa.properties`는 Map이라, 점이 든 키는 YAML 계층으로
오해될 수 있다. IDE도 `YAML_SHOULD_ESCAPE` 경고를 띄운다.

→ `"[org.hibernate.SQL]"`, `"[hibernate.format_sql]"` 처럼 `[]`로 감싼다.

이 과정에서 `hibernate.dialect` 명시가 불필요하다는 것도 확인했다
(`HHH90000025` 경고). Hibernate가 JDBC 연결을 보고 자동 선택하므로 제거했다.

### ⑧ `ddl-auto: update`는 컬럼을 지우지 않는다

엔티티에서 `source`를 지웠는데 DB 컬럼이 NOT NULL로 남아 **모든 INSERT가 실패**했다.
`update`는 이름 그대로 추가만 한다.

→ Flyway 도입으로 해결(5장). 컬럼 삭제·타입 변경·데이터 이관을 마이그레이션 파일로 관리한다.

### ⑨ Boot 4는 라이브러리만으로 자동설정이 붙지 않는다

`flyway-core`와 `flyway-database-postgresql`을 넣었는데 **오류도 없이 Flyway가 실행되지 않았다.**
로그에 한 줄도 안 나왔다.

원인은 Boot 4의 오토컨피그 모듈 분리였다. 연결 코드가 `spring-boot-flyway`라는 별도 모듈에 있다.
그 jar 안에는 이런 등록부가 들어 있다.

```
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
  └─ org.springframework.boot.flyway.autoconfigure.FlywayAutoConfiguration
```

이 등록부가 있어야 `spring.flyway.*` 설정을 읽는 코드가 동작한다.
**설정은 처음부터 맞았고, 그 설정을 해석할 어댑터 계층이 없었던 것이다.**
Spring Boot는 모르는 설정 키에 오류를 내지 않으므로 조용히 무시됐다.

같은 패턴을 오늘만 세 번 만났다.

| 3.x 기준 자료 | Boot 4 실제 |
|---|---|
| `spring-boot-starter-web` | `spring-boot-starter-webmvc` |
| `spring-boot-starter-test` | `-webmvc-test`, `-data-jpa-test` 등으로 분리 |
| `flyway-core` | `spring-boot-flyway` + `flyway-database-postgresql` |

**대응법**: "라이브러리는 넣었는데 반응이 없다" → BOM에서 대응 `spring-boot-*` 모듈을 찾는다.
BOM은 `~/.gradle/caches/modules-2/files-2.1/org.springframework.boot/spring-boot-dependencies/`
아래 POM 파일이며, `spring-boot-*` 모듈이 312개 정의돼 있다.
공식 문서의 Managed Dependency Coordinates 페이지에는 **서드파티 버전만** 있고
Spring Boot 자체 모듈은 없으므로 POM을 직접 봐야 한다.

진단에는 `bootRun --args='--debug'`의 자동설정 리포트가 유용하다.
`Positive matches` / `Negative matches`로 어떤 오토컨피그가 왜 적용되지 않았는지 나온다.

### ⑩ PostgreSQL LIKE와 역슬래시 구분자의 충돌

카테고리 구분자가 역슬래시인데, **PostgreSQL은 LIKE에서 역슬래시를 기본 이스케이프 문자로 취급**한다.
`LIKE '능력\%'`가 "능력으로 시작하는 하위 경로"가 아니라 "능력 뒤에 리터럴 %"로 해석된다.

→ `ESCAPE '!'`로 이스케이프 문자를 따로 지정해 역슬래시가 리터럴이 되게 했다.
사용자 입력의 `%`, `_`도 함께 이스케이프해 와일드카드 주입을 막는다.
