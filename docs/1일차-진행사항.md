## 3. 백엔드 (최종)

### 도메인

**Schedule**

| 필드 | 타입 | 비고 |
|---|---|---|
| `title` | String(200) | 필수 |
| `description` | TEXT | **마크다운 원문**. 렌더링은 화면 담당 |
| `startAt` / `endAt` | LocalDateTime | endAt은 선택 |
| `allDay` | boolean | |
| `status` | enum | PLANNED / DONE / SKIPPED |
| `category` | ManyToOne | LAZY, nullable(미분류 허용) |
| `createdAt` / `updatedAt` | LocalDateTime | JPA 감사 |

**Category** — 계층은 `parent_id`로 잡되 전체 경로 `path`를 함께 보관한다.

| 필드 | 비고 |
|---|---|
| `name` | 마지막 세그먼트만 (`능력\개발` → `개발`) |
| `parent` | 자기참조 |
| `path` | 루트부터의 전체 경로, unique |
| `displayOrder` / `color` / `collapsed` / `archived` | 사이드바 표시용 |

`path`를 중복 보관하는 대가로 **"하위 포함 필터"가 재귀 조회 없이 prefix 비교 한 번**으로 끝난다.
반대급부는 이름 변경 시 후손의 `path`도 갱신해야 한다는 점이고, `CategoryService.rename()`이 담당한다.

### 엔드포인트

**일정** `/api/schedules`

| 메서드 | 경로 | 응답 |
|---|---|---|
| GET | `?from=&to=&status=&category=` | 200 |
| GET | `/{id}` | 200 / 404 |
| POST | | 201 + Location |
| PUT | `/{id}` | 200 / 404 |
| PATCH | `/{id}/status` | 200 / 404 |
| DELETE | `/{id}` | 204 / 404 |

`category`는 **하위까지 포함**해 조회한다. `능력` → `능력\개발`은 걸리고 `능력강화`는 안 걸린다.
생성·수정 시 `categoryPath` 문자열을 받아 **없으면 중간 단계까지 만들어 붙인다**(get-or-create).

**카테고리** `/api/categories`

| 메서드 | 경로 | 비고 |
|---|---|---|
| GET | | 경로순 (부모가 자식보다 먼저) |
| POST | | 중간 단계 없으면 함께 생성 |
| PATCH | `/{id}/name` | 후손 경로 자동 갱신 |
| PATCH | `/{id}/appearance` | 색상·순서·접힘·보관 |
| DELETE | `/{id}` | **하위까지 함께 삭제**, 딸린 일정은 부모 카테고리로 승격 |

### 설계상 지킨 것

- **엔티티를 직접 반환하지 않는다.** DTO로 변환한다. `open-in-view: false` 환경에서
  지연 로딩이 직렬화 중 터지는 것을 막고, 엔티티 변경이 API 계약에 새지 않게 한다.
- **setter 대신 의도가 드러나는 메서드.** `update()`, `changeStatus()`, `rename()`만 열어둔다.
- **예외는 `@RestControllerAdvice`에서 일괄 변환.** 컨트롤러에 try-catch가 없다.
- **조회는 Specification(동적 쿼리).** 조건이 있을 때만 predicate를 붙인다.

## 5. 스키마 관리 — Flyway

`ddl-auto: update`는 컬럼 추가만 하고 **삭제와 타입 변경을 하지 않는다.**
실제로 `source` 필드를 지웠을 때 DB 컬럼이 NOT NULL로 남아 모든 INSERT가 실패했다.
스키마를 고치는 주체를 Flyway 하나로 통일하고 `ddl-auto`는 `validate`로 내렸다.

| 파일 | 내용 |
|---|---|
| `V1__init.sql` | 기존 스키마 베이스라인. 기존 DB에서는 기록만 되고 실행되지 않는다 |
| `V2__drop_source_and_widen_columns.sql` | source 제거, description → TEXT, category 확장 |
| `V3__add_category_table.sql` | category 테이블 생성 + 기존 문자열 이관 + FK 연결 |

실행 로그가 설계 그대로 나왔다.

```
Successfully baselined schema with version: 1
Migrating schema "public" to version "2 - drop source and widen columns"
Migrating schema "public" to version "3 - add category table"
```

**규칙: 이미 적용된 마이그레이션 파일은 수정 금지.** checksum이 어긋나면 앱이 기동을 거부한다.
변경이 필요하면 새 버전을 추가한다.

**V3의 데이터 이관** — `능력\개발\SpringBoot` 문자열 하나에서 상위 경로 3개를 모두 만들어야
계층이 완성되므로, `generate_series`로 경로 접두사를 펼쳐 넣고 `parent_id`를 연결했다.
테이블 생성·데이터 이관·FK 연결이 **한 파일에서 원자적으로** 처리된다 — `ddl-auto`로는 불가능한 부분.

## 6. 검증 결과

**API** — 일정 6개, 카테고리 5개 엔드포인트 동작 확인.

**에러 처리** — 모두 통일된 JSON으로 응답:

| 상황 | 코드 |
|---|---|
| title 누락 / endAt < startAt / 깨진 JSON / 잘못된 enum | 400 |
| 하위 있는 카테고리 삭제 | 400 + 안내 메시지 |
| 없는 id | 404 |

**카테고리 계층**

- 기존 문자열 4종 → 카테고리 7개로 이관, 부모 연결까지 정확
- 하위 포함 필터: `능력` 4건 / `능력\개발` 2건 / `취미` 1건 / `능력강화` 0건
- **이름 변경 `능력\개발` → `능력\학습` 한 번에 후손 2개 경로가 갱신되고 일정도 그대로 따라왔다.**
  FK 참조라 일정 테이블은 건드릴 필요가 없다 — 엔티티 승격의 실익이 확인된 지점
- 화면에서 `능력\개발\DB\Flyway` 입력 → `DB`, `Flyway` 두 단계가 자동 생성되어 사이드바에 반영

**카테고리 삭제**

| 대상 | 결과 |
|---|---|
| 하위가 있는 카테고리 | 204. 자신 + 후손 4개 삭제, 일정 3건은 부모로 승격 |
| 일정만 달린 카테고리 | 204. 일정 유지 |
| 최상위 카테고리 | 204. 일정은 미분류가 됨 |

**일정은 한 건도 유실되지 않았다.** 분류 정리 때문에 사용자가 남긴 기록이 사라지면 안 된다는 원칙.

**기타**

- 마크다운 원문(백틱·체크박스·인용문 포함) 왕복 일치
- LIKE 와일드카드(`%`) 주입 시 리터럴 처리
- 브라우저에서 등록·정렬·상태토글·삭제·필터 동작 확인, 콘솔 에러 없음

## 7. 구현 중 해결한 문제

오늘 가장 시간이 든 부분이자 재발 가능성이 있는 항목들.

### ① 한글 경로 때문에 테스트가 실행조차 안 됨

프로젝트 경로에 `바탕 화면`이 포함돼, Gradle이 UTF-8로 쓴 테스트 워커 `@argfile`을
Java 런처가 시스템 인코딩(CP949)으로 읽어 클래스패스가 깨졌다.
증상은 `ClassNotFoundException`인데 클래스 파일은 멀쩡히 존재하는 형태.

→ `gradle.properties`에 `org.gradle.jvmargs=-Dfile.encoding=MS949`로 해결.

**근본 대책은 프로젝트를 ASCII 경로로 옮기는 것.** OneDrive가 `node_modules`
수만 개 파일을 동기화하며 빌드 중 파일 잠금을 일으키는 문제도 함께 사라진다.

### ② Spring Boot는 `.env`를 자동으로 읽지 않는다

`.env`는 Node/Docker 관례라 `${DB_PASSWORD}`는 OS 환경변수만 찾는다.

→ `spring.config.import: optional:file:.env[.properties]` 로 해결.
`optional:`을 붙였으므로 `.env`가 없는 배포 환경에서도 앱은 정상 기동한다.

### ③ `:param is null` 패턴이 PostgreSQL에서 실패

기간·상태 조회를 JPQL `(:from is null or s.startAt >= :from)`로 짰더니
`$1 매개 변수의 자료형을 알수가 없습니다` 오류. PostgreSQL은 null 비교에만 쓰인
파라미터의 타입을 추론하지 못한다.

→ **Specification(동적 쿼리)** 으로 교체. 조건이 있을 때만 predicate를 붙이므로
생성되는 SQL도 더 깔끔하다.

### ④ 원시 `boolean`은 JSON 선택 필드로 쓸 수 없다

`allDay`를 생략하고 POST하면 `Cannot map null into type boolean`.

→ 요청 DTO에서 `Boolean` 래퍼를 쓰고 서비스에서 null을 false로 취급.

### ⑤ `updatedAt`이 갱신 전 값으로 응답됨

`@LastModifiedDate`는 flush 시점에 채워진다. 변경 감지만 믿고 바로 DTO를 만들면
응답에는 수정 전 `updatedAt`이 실린다.

→ 수정·상태변경 시 `saveAndFlush` 후 응답 생성.

### ⑥ 스택트레이스가 API 응답에 노출됨

에러 응답에 자바 스택트레이스가 통째로 실려 나왔다. devtools가
`include-stacktrace=always`를 기본으로 심기 때문.

→ `spring.devtools.add-properties: false`로 차단.

추가로 **Boot 4에서 `server.error.include-stacktrace`는 error 레벨로 폐기**되고
`spring.web.error.include-stacktrace`로 옮겨졌다. 3.x 기준 자료를 보고 옛 이름을 쓰면
조용히 무시된다.

### ⑦ YAML Map 키 이스케이프

`logging.level`과 `spring.jpa.properties`는 Map이라, 점이 든 키는 YAML 계층으로
오해될 수 있다. IDE도 `YAML_SHOULD_ESCAPE` 경고를 띄운다.

→ `"[org.hibernate.SQL]"`, `"[hibernate.format_sql]"` 처럼 `[]`로 감싼다.

이 과정에서 `hibernate.dialect` 명시가 불필요하다는 것도 확인했다
(`HHH90000025` 경고). Hibernate가 JDBC 연결을 보고 자동 선택하므로 제거했다.

### ⑧ `ddl-auto: update`는 컬럼을 지우지 않는다

엔티티에서 `source`를 지웠는데 DB 컬럼이 NOT NULL로 남아 **모든 INSERT가 실패**했다.
`update`는 이름 그대로 추가만 한다.

→ Flyway 도입으로 해결(5장). 컬럼 삭제·타입 변경·데이터 이관을 마이그레이션 파일로 관리한다.

### ⑨ Boot 4는 라이브러리만으로 자동설정이 붙지 않는다

`flyway-core`와 `flyway-database-postgresql`을 넣었는데 **오류도 없이 Flyway가 실행되지 않았다.**
로그에 한 줄도 안 나왔다.

원인은 Boot 4의 오토컨피그 모듈 분리였다. 연결 코드가 `spring-boot-flyway`라는 별도 모듈에 있다.
그 jar 안에는 이런 등록부가 들어 있다.

```
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
  └─ org.springframework.boot.flyway.autoconfigure.FlywayAutoConfiguration
```

이 등록부가 있어야 `spring.flyway.*` 설정을 읽는 코드가 동작한다.
**설정은 처음부터 맞았고, 그 설정을 해석할 어댑터 계층이 없었던 것이다.**
Spring Boot는 모르는 설정 키에 오류를 내지 않으므로 조용히 무시됐다.

같은 패턴을 오늘만 세 번 만났다.

| 3.x 기준 자료 | Boot 4 실제 |
|---|---|
| `spring-boot-starter-web` | `spring-boot-starter-webmvc` |
| `spring-boot-starter-test` | `-webmvc-test`, `-data-jpa-test` 등으로 분리 |
| `flyway-core` | `spring-boot-flyway` + `flyway-database-postgresql` |

**대응법**: "라이브러리는 넣었는데 반응이 없다" → BOM에서 대응 `spring-boot-*` 모듈을 찾는다.
BOM은 `~/.gradle/caches/modules-2/files-2.1/org.springframework.boot/spring-boot-dependencies/`
아래 POM 파일이며, `spring-boot-*` 모듈이 312개 정의돼 있다.
공식 문서의 Managed Dependency Coordinates 페이지에는 **서드파티 버전만** 있고
Spring Boot 자체 모듈은 없으므로 POM을 직접 봐야 한다.

진단에는 `bootRun --args='--debug'`의 자동설정 리포트가 유용하다.
`Positive matches` / `Negative matches`로 어떤 오토컨피그가 왜 적용되지 않았는지 나온다.

### ⑩ PostgreSQL LIKE와 역슬래시 구분자의 충돌

카테고리 구분자가 역슬래시인데, **PostgreSQL은 LIKE에서 역슬래시를 기본 이스케이프 문자로 취급**한다.
`LIKE '능력\%'`가 "능력으로 시작하는 하위 경로"가 아니라 "능력 뒤에 리터럴 %"로 해석된다.

→ `ESCAPE '!'`로 이스케이프 문자를 따로 지정해 역슬래시가 리터럴이 되게 했다.
사용자 입력의 `%`, `_`도 함께 이스케이프해 와일드카드 주입을 막는다.

## 11. 학습 기록

오늘 구현하면서 짚은 개념들. 면접 답변 재료로도 쓸 수 있게 "왜"를 중심으로 정리한다.

### 11-1. 영속성 컨텍스트와 엔티티 4가지 상태

| 상태 | 조건 | 수정하면 |
|---|---|---|
| **비영속** (transient) | `new`로 만듦, id 없음 | 아무 일 없음 |
| **영속** (managed) | 트랜잭션 안에서 조회/저장됨 | **커밋 시 UPDATE** |
| **준영속** (detached) | 트랜잭션이 끝나 관리 해제, id 있음 | 아무 일 없음 |
| **삭제** (removed) | `delete()` 호출됨 | 커밋 시 DELETE |

비영속과 준영속은 둘 다 "관리 안 됨"이지만 **`id` 유무가 다르고**, 그래서 `save()`의 동작이
갈린다. 비영속은 INSERT, 준영속은 merge(SELECT 후 UPDATE).

주의: 준영속 객체를 `save()` 하면 그 객체가 영속이 되는 게 아니라 **새로운 영속 인스턴스가
반환된다.** 원래 객체를 계속 쓰면 수정이 반영되지 않는다. `save()`의 반환값을 받아 쓸 것.

### 11-2. 변경 감지 — `save()` 없이 UPDATE가 되는 이유

`CategoryService.rename()`은 `save()`를 한 번도 부르지 않는데 DB가 바뀐다.

```java
Category category = checkAndGetId(id);   // 조회 → 영속 상태
category.rename(name, newPath);          // 필드만 변경
// 트랜잭션 종료 시 UPDATE 발생
```

영속 상태 엔티티는 **조회 시점의 스냅샷**을 함께 보관하고, 커밋할 때 비교해 바뀐 필드만
UPDATE한다.

**비교 대상은 DB의 현재 상태가 아니라 메모리에 떠둔 스냅샷이다.** 커밋할 때 DB를 다시 읽지
않는다. 그래서 내가 읽은 뒤 다른 트랜잭션이 그 행을 바꿔도 알아채지 못하고 덮어쓴다.
이를 막는 장치가 `@Version`을 이용한 낙관적 락.

`save()`가 정말 필요한 곳은 **새로 만든 엔티티**뿐이다. 그래서 `create()`에는 있고
`rename()`·`updateAppearance()`에는 없다 — 일관성이 없어 보이지만 의도된 차이.

### 11-3. `@Transactional`이 필요한 이유

Spring Data의 리포지토리 구현체에는 이미 `@Transactional`이 붙어 있어서, 단순 조회 한 번이면
서비스에 없어도 동작한다. 그런데 이 프로젝트 코드는 없으면 **조용히 망가진다.**

| 이유 | 이 프로젝트에서 |
|---|---|
| 원자성 | `rename()`·`delete()`는 여러 행을 고친다. 중간 실패 시 계층이 깨진 채 남음 |
| 변경 감지 | `save()` 없이 수정하는 코드가 전부 여기 의존 |
| LAZY 로딩 | `Schedule.category`가 LAZY. 트랜잭션 밖에서 접근하면 예외 |

`readOnly = true`를 클래스에 걸고 쓰기 메서드만 `@Transactional`로 덮어쓰는 패턴을 쓴다.
읽기 전용이면 변경 감지용 스냅샷을 만들지 않아 메모리와 CPU가 절약된다.

**경계는 메서드가 아니라 트랜잭션이다.** `ScheduleService.create()`가
`CategoryService.getOrCreate()`를 부를 때 `@Transactional`이 두 개지만 트랜잭션은 하나다
(기본 전파 옵션이 "있으면 참여"). 그래서 영속성 컨텍스트도 하나를 공유하고, 안쪽에서
반환한 엔티티가 바깥에서도 영속 상태로 남는다. 롤백도 함께 일어난다.

**함정 두 개**

- import는 `org.springframework.transaction.annotation.Transactional`. `jakarta` 쪽에는
  `readOnly`가 없다.
- 프록시 기반이라 **같은 클래스 안에서 자기 메서드를 부르면 적용되지 않는다.**
  `getOrCreate()`의 재귀 호출이 그 경우인데, 바깥 트랜잭션에 참여하므로 지금은 문제가 없다.
  다만 `REQUIRES_NEW`를 기대할 때는 조용히 무시되어 원인 찾기가 어렵다.

### 11-4. N+1 문제

**트랜잭션이 여러 번 생기는 게 아니라, 트랜잭션 하나 안에서 SELECT가 여러 번 나가는 문제.**

LAZY로 두면 목록 조회 시 연관 엔티티 자리에 프록시만 들어오고, 실제 값을 꺼내는 순간
그제서야 SELECT가 나간다. 목록을 순회하며 하나씩 꺼내니 행 수만큼 쿼리가 발생한다.

**현재 이 프로젝트에 실제로 있다.** `ScheduleService.search()`가 `ScheduleResponse.from()`에서
`schedule.getCategory()`를 건드리면서 일정마다 카테고리를 조회한다.

영속성 컨텍스트의 1차 캐시는 오히려 이를 **완화**한다. 이미 읽은 것은 다시 조회하지 않으므로
실제 쿼리 수는 행 개수가 아니라 서로 다른 카테고리 개수만큼이다.

무서운 이유는 **데이터가 늘어난 만큼 선형으로 악화**된다는 점. 개발 중에는 데이터가 적어
멀쩡해 보이다가 실제로 쓰기 시작하면 터진다.

| 방법 | 성격 |
|---|---|
| `default_batch_fetch_size` | 설정 한 줄. N번 → `IN` 한 번. 지금 규모엔 이걸 권함 |
| fetch join / `@EntityGraph` | 특정 조회만 확실히. 동적 쿼리와 섞이면 복잡 |
| EAGER로 전환 | **해결되지 않음.** 목록 쿼리에서는 여전히 행마다 SELECT가 나가고, 끌 수도 없음 |

정석은 **전부 LAZY로 두고 필요한 조회에만 최적화를 켜는 것.** 끄는 것보다 켜는 게 쉽다.
`@ManyToOne`은 기본값이 EAGER라 명시적으로 LAZY를 적어야 한다.

### 11-5. 연관관계

**연관 데이터 = FK로 이어진 행.** 대개 다른 테이블이지만 `Category.parent`처럼 자기 자신을
가리킬 수도 있다.

- **FK 컬럼을 가진 쪽이 연관관계의 주인**이고, 그쪽에서만 값을 바꿀 수 있다.
- FK 하나로 자바에서는 최대 두 방향(`@ManyToOne` / `@OneToMany`)을 만들 수 있다.
- 현재 프로젝트에는 `@OneToMany` 컬렉션이 하나도 없다. 컬렉션은 N+1 규모가 훨씬 크고
  여러 개를 fetch join하면 카테시안 곱 문제까지 생기므로, **양방향은 필요할 때만** 만든다.

`Category`에 `children` 컬렉션이 없어서 JPA는 자식의 존재를 모른다. 그래서
`categoryRepository.delete(category)` 한 줄로는 후손이 지워지지 않고 FK 위반이 난다.

### 11-6. Specification (동적 쿼리)

조건이 선택적일 때 쓴다. 람다의 세 인자는 `root`(FROM 절 시작점), `query`(쿼리 전체),
`cb`(조건 생산 공장).

**`null`을 반환하면 "조건 없음"으로 취급되어 건너뛴다.** 선택적 필터가 이렇게 구현된다.

`inCategory()`가 `OR` 두 개인 이유:

| 조건 | 담당 |
|---|---|
| `path = '능력\개발'` | 자기 자신 |
| `path LIKE '능력\개발\%'` | 하위 전부 |

`LIKE '능력\개발%'` 하나로 하면 `능력\개발자`까지 걸리고, 구분자를 붙이면
정작 자기 자신이 빠진다. 그래서 둘을 묶어야 한다.

`root.join()`은 **조건을 걸기 위한 조인**이라 엔티티를 채워주지 않는다. 카테고리로
필터링해도 N+1은 그대로 발생한다. 채우려면 `root.fetch()`를 써야 한다.

### 11-7. Flyway

**`ddl-auto: update`는 컬럼 추가만 하고 삭제·타입 변경을 하지 않는다.** 엔티티에서 필드를
지워도 DB 컬럼은 NOT NULL로 남아 INSERT가 전부 실패한다. 실제로 겪었다.

Flyway는 스키마 변경을 파일로 관리하고, 이력 테이블(`flyway_schema_history`)을 보고
**아직 적용되지 않은 것만** 앱 시작 시 실행한다. git이 코드에 하는 일을 스키마에 한다.

- 파일명은 `V4__설명.sql`. **밑줄 두 개.**
- **이미 적용된 파일은 수정 금지.** checksum이 어긋나면 앱이 기동을 거부한다.
  변경이 필요하면 새 버전을 추가한다.
- 기존 DB에 도입할 때는 `baseline-on-migrate`로 현재 상태를 특정 버전으로 간주시킨다.
- `ddl-auto`는 `validate`로 내린다. 스키마를 고치는 주체가 둘이면 서로 덮어쓴다.
  `validate`는 엔티티와 테이블이 어긋나면 기동 시점에 알려주는 안전망이 된다.
- **DBeaver에서 직접 ALTER 하지 말 것.** Flyway가 그 사실을 모르면 다른 환경과 스키마가
  어긋난다. DBeaver는 확인용으로만 쓴다.

### 11-8. Spring Boot 4의 자동설정 모듈 분리

`flyway-core`를 넣었는데 **오류도 없이 Flyway가 실행되지 않았다.** 로그에 한 줄도 없었다.

원인은 설정 오류가 아니라 **어댑터 계층의 부재**였다. `application.yml`의 설정은 처음부터
맞았지만, 그 설정을 읽어 동작시킬 자동설정 코드가 클래스패스에 없었다.

```
application.yml (설정값)
      ↓
 ??? AutoConfiguration    ← 이 계층이 있어야 값이 의미를 가짐
      ↓
  라이브러리 (flyway-core)
```

자동설정은 내가 쓰는 파일이 아니라 **jar 안에 들어 있는 자바 코드**이고,
`META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`라는
등록부에 선언되어 있다. Boot 3.x까지는 `spring-boot-autoconfigure` 하나에 뭉쳐 있었지만
**Boot 4에서 기능별 모듈로 쪼개졌다.**

Spring Boot는 모르는 설정 키에 오류를 내지 않으므로 조용히 무시된다. 오히려 오타였다면
오류가 났을 것이다.

| 3.x 기준 자료 | Boot 4 실제 |
|---|---|
| `spring-boot-starter-web` | `spring-boot-starter-webmvc` |
| `spring-boot-starter-test` | `-webmvc-test`, `-data-jpa-test` 등으로 분리 |
| `flyway-core` | `spring-boot-flyway` + `flyway-database-postgresql` |

**대응법**: "라이브러리는 넣었는데 반응이 없다" → BOM에서 대응 `spring-boot-*` 모듈을 찾는다.
BOM은 `~/.gradle/caches/.../spring-boot-dependencies/` 아래 POM 파일이며
`spring-boot-*` 모듈이 312개 정의돼 있다. 공식 문서의 Managed Dependency Coordinates
페이지에는 서드파티 버전만 있고 Spring Boot 자체 모듈은 없다.

진단은 `bootRun --args='--debug'`의 자동설정 리포트(`Positive/Negative matches`).

### 11-9. PostgreSQL LIKE와 역슬래시

**PostgreSQL은 LIKE에서 역슬래시를 기본 이스케이프 문자로 취급한다.** 계층 구분자가
역슬래시라 충돌한다. `LIKE '능력\%'`가 "능력으로 시작하는 하위 경로"가 아니라
"능력 뒤에 리터럴 % 문자"로 해석된다.

`ESCAPE '!'`로 이스케이프 문자를 바꿔 역슬래시를 평범한 글자로 만들었다. 사용자 입력의
`%`, `_`도 이스케이프해 와일드카드 주입을 막는다.

참고로 `LIKE 'prefix%'`가 btree 인덱스를 타려면 DB 로케일이 `C`이거나 인덱스를
`varchar_pattern_ops`로 만들어야 한다. 지금은 카테고리 행이 적어 순차 스캔이 오히려 빠르므로
필요 없다. 필요해지면 `EXPLAIN ANALYZE`로 확인 후 판단한다.

### 11-10. FK 제약과 삭제 순서

카테고리를 지울 때 두 개의 FK가 막는다.

| 제약 | 원인 |
|---|---|
| `category_parent_id_fkey` | 자식이 부모를 참조 |
| `fk_schedule_category` | 일정이 카테고리를 참조 |

그래서 순서가 중요하다.

1. 자신 + 후손 수집 (`path` prefix 한 번으로. 재귀 조회 불필요 — path를 중복 보관한 이점)
2. 일정을 먼저 떼어냄 (부모로 승격, 최상위면 미분류)
3. 카테고리 삭제

3번에서 `deleteAllByIdInBatch`를 쓰면 `delete ... where id in (...)` **한 문장**이 나간다.
PostgreSQL은 FK 검사를 문장 종료 시점에 하므로 부모와 자식이 같이 사라져 위반이 발생하지
않는다. 한 건씩 지운다면 **자식부터** 지우도록 정렬해야 한다.
