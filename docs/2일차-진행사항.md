## 1. JVM 크래시 11건 진단

프로젝트 폴더에 `hs_err_pid*.log` 11개와 `replay_pid*.log` 5개가 생겨 있었다.
"VM 오류"로 보이지만 JVM 버그가 아니었다.

```
# There is insufficient memory for the Java Runtime Environment to continue.
# Native memory allocation (malloc) failed to allocate 310416 bytes
#  Out of Memory Error (arena.cpp:168)
Current thread: JavaThread "C2 CompilerThread0"
```

크래시 시점의 시스템 상태가 원인을 말해줬다.

```
physical 32471M (704M free)                  ← 32GB 중 700MB만 남음
TotalPageFile 130775M (AvailPageFile 592M)   ← 130GB 페이지파일도 소진
MaxHeapSize = 8514437120  {ergonomic}        ← 8.5GB, JVM 기본값
```

`{ergonomic}` 은 **`-Xmx` 가 지정되지 않아 JVM이 기본값(물리 메모리의 1/4)을 골랐다**는 뜻이다.
11건 전부 Gradle 데몬 프로세스였다.

**원인은 어제 넣은 우회 설정이었다.** `org.gradle.jvmargs` 는 값을 추가하는 게 아니라
Gradle 기본 JVM 옵션을 **통째로 대체한다.** 인코딩만 적고 힙 상한을 빠뜨리자 두 가지가 겹쳤다.

1. 힙 상한이 JVM 기본값 8.5GB로 올라감
2. 지정한 JVM 옵션이 현재 프로세스와 달라 **빌드마다 새 JVM을 포크**
   (`To honour the JVM settings for this build a single-use Daemon process will be forked`)

8.5GB를 예약하는 JVM이 십수 개 쌓이며 130GB 페이지파일이 바닥났다.

→ 힙 상한 명시(`-Xmx2g -XX:MaxMetaspaceSize=512m`), 빌드 시 `--no-daemon` 제거로 데몬 재사용.
크래시 로그는 `.gitignore` 에 추가.

## 2. ASCII 경로로 이전

1번의 근본 원인은 결국 **한글 경로**였다. 인코딩 문제를 우회하려고 넣은 설정이 2차 피해를 낳았으니,
원인을 제거하는 게 맞았다.

```
이전:  C:\Users\maruc\OneDrive\바탕 화면\ProgrammingProjects\LonelyTracker
현재:  C:\ProgrammingProjects\LonelyTracker
```

**이전 후 인코딩 우회 설정을 제거하고 캐시를 지운 상태에서 테스트가 통과했다.**
어제는 이 설정 없이 `ClassNotFoundException` 으로 테스트가 실행조차 안 됐으므로,
**한글 경로가 원인이었음이 확정됐다.**

부수 효과로 OneDrive를 벗어나면서 `node_modules` 수만 개 파일 동기화로 빌드 중
파일이 잠기는 문제도 사라졌다.

남긴 설정은 메모리 상한뿐이다.

```properties
org.gradle.jvmargs=-Xmx2g -XX:MaxMetaspaceSize=512m
```

## 3. 테스트 기반 구축

### 발견한 두 가지 문제

**① 테스트가 개발 DB에 직접 붙고 있었다**

```
Test worker | FlywayExecutor : Database: jdbc:postgresql://localhost:5432/lonelytracker
```

`src/test/resources` 가 없어 테스트가 운영용 `application.yml` 을 그대로 썼다.
당시엔 `contextLoads` 하나뿐이라 무해했지만, **데이터를 쓰는 테스트를 추가하는 순간
실제 일정과 카테고리를 지웠을 것이다.**

**② 테스트가 0개인데 빌드는 성공했다**

경로 이전 과정에서 테스트 파일 위치가 납작해졌다.

```
정상:  src/test/java/com/lonelytracker/backend/BackendApplicationTests.java
당시:  src/test/BackendApplicationTests.java
```

Gradle은 `src/test/java` 아래만 소스로 인식하므로 이 파일은 무시됐다.

```
> Task :compileTestJava NO-SOURCE
> Task :test NO-SOURCE
BUILD SUCCESSFUL
```

**`NO-SOURCE` 는 오류가 아니라 "할 일 없음"이라 초록불이 뜬다.**
테스트가 사라졌는데 아무도 모르는, 가장 위험한 형태였다.

→ 위치 복구 + `testLogging` 을 켜서 실행된 테스트 목록이 콘솔에 보이게 했다.

### Testcontainers를 고른 이유

| 방법 | 판단 |
|---|---|
| H2 (인메모리) | **탈락.** 마이그레이션의 `generate_series`, 조회의 `LIKE ... ESCAPE` 같은 PostgreSQL 전용 문법이 안 돌아간다. 통과하는데 실제로는 깨지는 최악 |
| 별도 테스트 DB | 로컬에만 존재. CI에서 재현 불가 |
| **Testcontainers** | 채택. 테스트마다 일회용 PostgreSQL 컨테이너 |

어제 삭제 버그가 결정적 근거였다. 그 버그는 **FK 제약 위반**이었는데 FK는 DB에만 있다.
가짜 DB나 mock으로 테스트했다면 통과했을 것이다.
**이 프로젝트는 DB와 맞물리는 지점에서 사고가 났으니 통합 테스트가 맞다.**

부수 효과로 **빈 DB에서 시작하므로 `V1__init.sql` 이 매번 실행된다.**
개발 DB에서는 baseline 처리되어 한 번도 실행된 적 없던 파일이다.

### 구성

```java
public abstract class IntegrationTest {
    static final PostgreSQLContainer POSTGRES = new PostgreSQLContainer("postgres:17-alpine");
    static { POSTGRES.start(); }          // 클래스마다가 아니라 전체에서 한 번

    @DynamicPropertySource
    static void datasourceProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", POSTGRES::getJdbcUrl);
        ...
    }
}
```

`@DynamicPropertySource` 는 **우선순위가 가장 높아** `application.yml` 의 `${DB_PASSWORD}` 를
아예 쳐다보지 않는다. `.env` 가 없는 환경에서도 동작한다.

## 4. 사용자 도입과 카테고리 구조 전환

### 결정을 뒤집었다

1일차에 "단일 사용자, `userId` 없음"으로 확정했으나 2일차에 **User 도입으로 변경**했다.
카테고리를 사용자별로 관리하려면 소유자 개념이 필요했기 때문이다.

동시에 **카테고리 계층을 폐기**했다. TickTick식 하위 목록은 카테고리가 아니라
일정 쪽에 두는 게 맞다고 판단했고, 계층 관리 비용이 얻는 것보다 컸다.

### 구조 변화

| | 1일차 (V3) | 2일차 (V4) |
|---|---|---|
| 카테고리 저장 | `category` 테이블, `parent_id`+`path` 계층 | `user_category`, 평평한 목록 |
| 일정의 분류 | `category_id` FK | **`category` 문자열** |
| 소유자 | 없음 | `app_user` + `schedule.user_id` |

### 카테고리를 다시 문자열로 되돌린 이유

1일차에 문자열 → 엔티티로 승격했고, 2일차에 다시 문자열로 되돌렸다. 실패가 아니라 요구 변화다.

> 카테고리 목록에서 "능력"을 지우거나 이름을 바꿔도,
> **이미 기록한 일정의 분류는 그대로여야 한다.** 과거 기록은 그 시점의 사실이다.

FK로 묶으면 이게 불가능하다. 지우려면 참조를 끊거나 함께 지워야 한다.
1일차 삭제 로직에서 씨름했던 게 정확히 그 문제였다.

**원칙: "현재 상태"는 참조로, "그때의 기록"은 값으로.**
주문 시점의 상품 가격을 주문 테이블에 복사해 넣는 것과 같은 이치다.

이 판단은 테스트로 못박아 두었다 — FK로 되돌리면 즉시 실패한다.

### V4 마이그레이션 (5단계)

1. `app_user` 생성 + 기본 사용자 삽입
2. `user_category` 생성 + 기존 category를 **경로 마지막 조각만** 이관
3. `schedule.user_id` 추가 → 값 채움 → `NOT NULL` + FK
4. `schedule.category` 문자열 컬럼 추가 → 마지막 조각 복사 → `category_id` 제거
5. 계층 기반 `category` 테이블 DROP

3번의 순서가 중요하다. **nullable로 추가 → 값 채움 → NOT NULL 전환** 해야
기존 행이 있는 테이블에서 실패하지 않는다.

**데이터는 전부 보존됐다.**

```
능력\커리어   →  커리어
취미\게임개발 →  게임개발
```

일정 6건, 카테고리 4개 모두 유지.

### 소유자 격리

```java
Specification<Schedule> spec = Specification
        .allOf(ScheduleSpecs.ownedBy(currentUserProvider.get().getId()))   // 항상
        .and(...);
```

단건 접근은 소유자 불일치 시 **404** 를 낸다. 403은 "그 id는 존재하지만 네 것이 아니다"를
알려주므로 남의 데이터 존재 여부가 샌다.

`CurrentUserProvider` 는 **임시 구현**이다. 인증이 없어 항상 기본 사용자를 반환하지만,
서비스·컨트롤러에는 이미 소유자 개념이 흐른다. **OAuth를 붙일 때 이 클래스만 교체하면 된다.**

### 부수 효과 — N+1이 사라졌다

1일차에 확인했던 N+1(일정 목록 조회 시 카테고리를 하나씩 조회)이 저절로 없어졌다.

```java
public record ScheduleResponse(..., String category, ...)   // 더 이상 연관 엔티티가 아님
```

`category` 가 문자열이라 지연 로딩할 게 없다. `Schedule.user` 는 LAZY지만 응답에 포함되지 않고,
소유자 검사도 `getId()` 만 쓰는데 이건 프록시에서 바로 나오므로 조회가 발생하지 않는다.

**설계를 바꿨더니 성능 문제가 따라서 사라진** 경우다.

## 5. 설정과 상수 정리

하드코딩된 값이 흩어져 있어 정리했다. **성격이 두 종류라 관리 방법도 나눴다.**

| 종류 | 어디에 | 예 |
|---|---|---|
| 운영 중 바뀔 수 있는 값 | `application.yml` + `AppProperties` | 기본 사용자명, 추천 카테고리 |
| DB 스키마와 짝인 값 | `FieldLengths` 상수 클래스 | 길이 제한 200·50·20000 |

### 왜 길이 제한은 설정으로 못 빼는가

**자바 언어 제약이다.** `@Size(max = ...)` 는 어노테이션 속성인데, 명세상 어노테이션 값은
**컴파일 시점 상수**여야 한다.

```java
@Size(max = FieldLengths.TITLE)        // ✅ static final int
@Size(max = appProperties.title())     // ❌ 컴파일 오류
```

설정 파일 값은 앱이 뜬 뒤에 정해지는데 어노테이션은 컴파일할 때 확정돼야 한다. 시점이 다르다.

두 번째 이유도 있다. 이 값들은 DB 컬럼과 짝이라(`TITLE = 200` ↔ `VARCHAR(200)`),
환경마다 다르면 `ddl-auto: validate` 가 기동을 막는다.
**환경마다 달라지면 안 되는 값은 애초에 설정이 아니다.**

엔티티와 DTO가 같은 상수를 보게 해서, 1일차에 있었던 "DTO는 255자 허용인데 컬럼은 100자"
같은 어긋남이 구조적으로 불가능해졌다.

### username 규칙 제거 (V5)

OAuth로만 로그인을 받기로 하면서 기존 패턴이 **버그가 될 뻔했다.**

```
@Pattern(regexp = "[A-Za-z0-9_-]+")
someone@example.com  →  400 Bad Request   ← 로그인 붙이는 순간 전부 거부
```

제공자가 주는 이메일이나 식별자를 우리가 형식으로 제한할 수 없다.
→ 규칙 제거, 컬럼을 50 → 100자로 확장(V5). 테스트도 반대로 뒤집었다.

### 예외 패키지 정리

```
common/exception/
├─ GlobalExceptionHandler.java
├─ NotFoundException.java
├─ UserNotFoundException.java      ← user 패키지에서 이동
└─ CategoryNotFoundException.java  ← user 패키지에서 이동
```

**참고**: 도메인 예외를 `common` 으로 옮기면 도메인이 공통 패키지에 의존하게 된다.
지금 규모에선 찾기 쉬워 낫지만, 커지면 보통 도메인 예외는 각자 패키지에 두고
`common` 에는 기반 클래스와 핸들러만 남긴다.

## 7. 겪은 문제

### ① Boot 4에서 위치가 바뀐 것 (계속)

1일차 Flyway에 이어 테스트를 붙이며 세 개를 더 만났다.

| 예상한 이름 | Boot 4 실제 |
|---|---|
| `com.fasterxml.jackson.databind.ObjectMapper` | **`tools.jackson.databind.ObjectMapper`** (Jackson 3) |
| `...test.autoconfigure.web.servlet.AutoConfigureMockMvc` | **`...webmvc.test.autoconfigure.AutoConfigureMockMvc`** |
| `org.testcontainers:postgresql` | **`org.testcontainers:testcontainers-postgresql`** (2.x) |

특히 **Jackson 3** 은 그룹부터 `com.fasterxml.jackson` → `tools.jackson` 으로 바뀌었다.
온라인 자료는 전부 2.x 기준이다.

**대응법은 추측하지 않고 실물을 확인하는 것이다.** BOM의 POM 파일과 jar 안의 클래스 목록을
직접 열어 확인했다.

### ② 셸을 거칠 때 역슬래시가 먹힌다

이 환경에서 반복적으로 겪는 문제다.

- 정규식 `"[^\\\\/...]"` 이 `"[^\\/...]"` 로 줄어 컴파일 오류
- 치환 스크립트의 `\1` 이 제어문자 `0x01` 로 들어가 **8개 파일의 첫 import가 파손**

컴파일 오류로 바로 드러나 복구했지만, **역슬래시가 들어가는 내용은 파일 도구로 직접 쓰는 게 안전**하다.

## 10. 학습 기록

### 10-1. Lombok은 컴파일에 끼어드는 도구다

```
.java 소스 → javac 시작 → ★ Lombok이 메서드 추가 → .class 생성
```

**소스 파일은 그대로다.** 게터가 파일에 써지는 게 아니라 컴파일 도중 메모리에서만 추가된다.
그래서 `.java` 를 열면 없고 `javap` 로 `.class` 를 보면 있다.
IDE에 플러그인이 필요한 이유도 이것이다.

의존성이 `compileOnly` + `annotationProcessor` 두 줄인 이유도 여기 있다.
컴파일이 끝나면 결과물은 평범한 자바 클래스라 **실행 시점에는 Lombok이 필요 없다.**

`User.java` 는 소스 61줄에 직접 쓴 메서드가 하나뿐인데, 컴파일 결과에는 8개가 들어 있다.

### 10-2. `@RequiredArgsConstructor`

`final` 필드(와 `@NonNull` 필드)만 골라 생성자를 만든다.
Spring 4.3부터 **생성자가 하나면 `@Autowired` 생략**이 가능해, 필드만 선언하면 주입이 끝난다.

필드 주입 대신 쓰는 이유:

- `final` 을 붙일 수 있어 주입 후 바뀌지 않는다
- 부품이 없으면 **앱 기동 시점에** 실패한다 (필드 주입은 실제 호출 때 NPE)
- 테스트에서 `new ScheduleService(mockA, mockB)` 로 바로 만들 수 있다
- 생성자 인자가 많아지면 "이 클래스가 일을 너무 한다"가 눈에 보인다

**주의**: 필드 선언 순서 = 생성자 인자 순서. 같은 타입 필드가 둘 이상이면 순서를 바꿨을 때
조용히 뒤바뀐다.

### 10-3. 엔티티는 Lombok, DTO는 `record`

`record` 는 게터·생성자·`equals`·`hashCode`·`toString` 을 자바 문법 자체가 만들어준다.
그런데 엔티티는 JPA가 기본 생성자와 가변 필드를 요구해서 `record` 로 만들 수 없다.

엔티티의 생성자 조합에도 의도가 있다.

```java
@NoArgsConstructor(access = AccessLevel.PROTECTED)   // JPA가 요구
@AllArgsConstructor(access = AccessLevel.PRIVATE)    // 빌더 전용
@Builder
```

`public` 으로 열면 아무나 `new Schedule()` 로 빈 껍데기를 만들 수 있어 `PROTECTED` 로 막고,
정상 생성은 빌더로만 하게 했다. `@Setter` 와 `@Data` 는 쓰지 않는다 —
세터가 열리면 아무 데서나 상태가 바뀌고, `@Data` 의 `toString` 이 연관 엔티티를 타고 가다
무한 순환하거나 LAZY 로딩을 터뜨린다.

### 10-4. 국제화는 세 계층으로 나뉜다

나중에 다국어를 지원한다면 `application.yml` 하나로 되지 않는다.

| 무엇 | 어디에 | 이유 |
|---|---|---|
| 기본 언어 스위치 | `application.yml` (`spring.web.locale`) | 값 하나 |
| 실제 문구 | `messages_ko.properties` 등 | 수백 개. yml에 넣으면 감당 안 됨 |
| 사용자별 선택 언어 | **DB** | 사용자마다 다른 **데이터** |
| 화면 문구 | 프론트 `locales/*.json` | 백엔드 yml은 브라우저까지 가지 않음 |

일반화하면 이 기준이 계속 쓰인다.

```
앱 전체에 하나, 환경마다 다를 수 있음  → application.yml
양이 많은 콘텐츠                      → 전용 파일
사용자마다 다름                        → DB
코드와 스키마가 함께 지켜야 함          → 상수 클래스
```

### 10-5. Flyway 파일은 쌓여도 된다

"마이그레이션 파일이 계속 늘어나는 걸 막아야 하지 않나"를 검토했다. **결론은 아니다.**

- 현재 5개, 합쳐서 150줄 남짓. 실무 프로젝트는 수백 개가 흔하다
- 기동 시 이력 테이블과 **체크섬만 비교**하므로 비용이 거의 없다
- 이미 적용된 파일은 수정 금지라, 합치려면 절차(squash + repair)가 필요하다
- 합치면 **변경 이력의 맥락이 사라진다**

정리할 적기는 **첫 배포 직전**이다. 그때는 개발 DB를 비우고 처음부터 만들어보는 절차가
어차피 필요하고, squash와 자연스럽게 겹친다.

덧붙여, Testcontainers 도입으로 **매 테스트마다 빈 DB에서 V1부터 전부 실행**되므로
과거 파일이 여전히 유효한지 자동 검증된다. 파일이 늘어도 썩지 않는 구조가 됐다.

## 11. 다음에 할 일

포트폴리오 관점에서 **기능을 넓히기보다 이미 만든 것을 보이게 만드는 게 먼저**라고 판단했다.

**우선순위 높음**

- **화면 스크린샷** — README에 자리만 있고 비어 있다. 첫인상을 좌우한다
- **자연어 입력 파싱** — `"내일 3시 회의"` → 일정 등록. 이게 없으면 프로젝트 이름이 참이 아니다
- **배포** — 프론트 빌드를 백엔드 `static/` 에 넣어 JAR 하나로

**화면 작업**

- 마크다운 렌더링 (`react-markdown`) + **체크리스트를 하위 목록으로 표시**
- 카테고리 관리 UI — API는 있는데 화면 진입점이 없다
- 수정 화면 — `PUT` API는 있으나 진입점 없음
- 날짜별 그룹핑, 오늘/이번 주 필터

**보류하기로 한 것**

기능 10개를 반쯤 만든 것보다 3개를 제대로 만든 게 낫다는 판단.

- OAuth 로그인 — 소유 구조는 갖췄으므로 "다음 단계"로 설명 가능
- 기능 On/Off 토글 — 범위 미정, 차별화 효과 낮음
- 국제화 — 10-4의 결론대로

**미결 사항**

- 목록에 없는 카테고리 이름도 일정에 저장된다. 자유 입력을 허용한 결과인데,
  **목록에서 지운 분류를 가진 일정을 화면에서 어떻게 찾을지**는 정하지 않았다
- `CurrentUserProvider` 가 임시 구현이다. 공개 배포 시 누구나 기본 사용자가 된다
