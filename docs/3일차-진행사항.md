## 1. Tailwind CSS v4 도입

### v4는 설정 파일이 없다

v3까지 쓰던 `tailwind.config.js` 가 사라지고 **CSS 안에서 설정한다.**

```css
@import "tailwindcss";

@theme {
  --color-brand-500: #0ea5e9;
}
```

`@theme` 의 변수는 두 가지 일을 동시에 한다.

1. `:root` 에 실제 CSS 변수로 출력 → `var(--color-brand-500)`
2. **유틸리티 클래스를 만들어낸다** → `bg-brand-500`, `text-brand-500`, `border-brand-500`

이름 앞의 `--color-` 는 "색상 계열"이라는 표시라 반드시 붙여야 한다. 빼면 유틸리티가 생기지 않는다.

### 설치는 세 단계

```
① npm i -D tailwindcss @tailwindcss/vite
② vite.config.ts 에 플러그인 등록
③ index.css 맨 위에 @import "tailwindcss"
```

`@import` 가 **맨 위**에 있어야 한다. preflight(기본 리셋)를 먼저 깔고 그 위에 직접 쓴 규칙이 올라가야 덮어쓸 수 있다.

### 전환은 색을 토큰으로 묶는 것부터

기존에 손으로 쓴 CSS에 이미 `--brand-500` 같은 변수를 두고 있었다. 그래서 전환 순서를 이렇게 잡았다.

```
① @theme 에 색을 옮긴다
② 기존 변수는 별칭으로 남긴다   --brand-500: var(--color-brand-500)
   → 기존 CSS 와 Tailwind 유틸리티가 같은 색 하나를 본다
③ 컴포넌트를 하나씩 className 으로 옮긴다
④ 다 옮기면 App.css 를 지운다
```

한 번에 갈아엎지 않고 **공존 구간을 만든 것**이 요점이다. 중간에 화면이 깨지지 않는다.

### 남은 CSS는 34줄

전환 후 `index.css` 에는 토큰과 두 규칙만 남았다.

```css
html { background-color: ...; }   /* 페이지 바탕색 */
body { min-width: 60rem; }        /* 최소 폭 */
```

`html`·`body` 에는 `className` 을 붙일 곳이 없어서 유틸리티로 대체할 수 없는 유일한 부분이다.

## 2. 겪은 문제

### ① `Unknown at rule @theme` 경고 — 빌드 오류가 아니었다

에디터가 `@theme` 에 빨간 줄을 그었다. 처음에는 `@types` 문제로 의심했는데 아니었다.

| | 담당 |
|---|---|
| 자동완성·색상 미리보기 | Tailwind 확장 |
| **`@theme` 경고** | **VS Code 내장 CSS 검사기** |

`@types/*` 는 자바스크립트 라이브러리의 타입 정의라 **`.css` 파일과 아무 관계가 없다.**
내장 검사기는 표준 CSS at-rule(`@media`, `@import` 등)만 알아서, Tailwind가 만든 `@theme` 을 모르는 규칙으로 본다.

**Tailwind 확장을 깔아도 사라지지 않는다.** 확장은 자동완성을 얹을 뿐 내장 검사기를 끄지 않는다. 두 기능의 주체가 다르다.

→ `.vscode/settings.json` 에 `"css.lint.unknownAtRules": "ignore"`.

**교훈**: 빌드는 VS Code가 아니라 Vite가 한다. 에디터 경고와 빌드 실패를 구분하는 습관이 필요하다. 실제로 빌드는 처음부터 정상이었다.

### ② Tailwind는 오타 난 클래스를 조용히 무시한다

`bg-brand-500` 을 `bg-brnad-500` 으로 잘못 쓰면 **아무 일도 일어나지 않는다.** 오류도 경고도 없고, 그냥 스타일이 안 먹는다.

그래서 전환 후 **빌드 결과 CSS에 선택자가 실제로 생성됐는지** 스크립트로 확인했다.

```js
// Tailwind 는 선택자에서 : [ ] . 앞에 백슬래시를 붙인다
const escapeSelector = (name) => '.' + name.replace(/[:[\].]/g, (ch) => '\\' + ch)
css.includes(escapeSelector('hover:bg-brand-600'))
```

`hover:bg-brand-600` 은 CSS에서 `.hover\:bg-brand-600:hover` 로 나온다. 이걸 모르고 그냥 문자열로 찾으면 "생성 안 됨"으로 잘못 판단하게 된다(실제로 한 번 헛짚었다).

### ③ 달력이 하루치 데이터만 받던 문제

날짜를 클릭하면 **다른 칸의 일정이 전부 사라졌다.**

원인은 상태 하나를 두 용도로 쓴 것이었다.

```
날짜 클릭 → 서버 조회를 그 하루로 좁힘 → schedules 가 하루치가 됨
          → 달력도 같은 schedules 를 보니 나머지 칸이 빈다
```

달력은 **한 달 전체**가 필요하고 목록은 **하루**가 필요한데, 둘이 같은 상태를 공유했다.

→ 서버 조회는 분류까지만 좁히고, 날짜 필터는 화면단에서 건다.

```tsx
const visibleSchedules = selectedDate
  ? schedules.filter((s) => isSameDay(new Date(s.startAt), selectedDate))
  : schedules;
```

**교훈**: "무엇을 조회할 것인가"와 "무엇을 보여줄 것인가"는 다른 문제다. 화면 두 곳이 같은 데이터를 다른 범위로 필요로 하면, 상태를 나누거나 파생시켜야 한다.

## 3. 학습 기록

### 3-1. 컴포넌트 폴더는 "도메인을 아는가"로 나눈다

화면의 어느 부분인지가 아니라 **그 컴포넌트가 도메인 지식을 갖는지**가 기준이다.

| 구분 | 도메인 지식 | 예 |
|---|---|---|
| `ui/` | 모름. 어디에나 붙음 | `Button`, `Chip` |
| `layout/` | 모름. 화면 뼈대만 | `AppShell`, `Header`, `SideMenu` |
| `features/` | **앎** | `ScheduleList` (Schedule 타입을 안다) |

`NavContainer` 처럼 이름에 `Container` 가 붙는 것들은 두 종류가 섞여 있다.

```tsx
// ① 순수 껍데기 — 안에 뭐가 오든 모름 → layout/
function NavContainer({ children }) { ... }

// ② 내용까지 아는 것 → features/
function CategorySidebar({ categories, onSelect }) { ... }
```

**단계적으로 나누는 게 좋다.** 컴포넌트 3개에 `features/` 까지 만들면 폴더가 파일보다 많아진다. 지금은 `layouts/` 만 만들고, 기능이 늘 때 `features/` 로 옮기기로 했다.

기능 단위로 모으는 것(colocation)의 이점은 **"기능을 뺀다 = 폴더 하나 삭제"** 가 된다는 점이다. 지금은 일정 관련 코드가 세 폴더에 흩어져 있다.

### 3-2. `useMemo` 는 렌더링을 막지 않는다

배운 설명 "렌더링 시 다시 계산하지 않는다"에는 오해가 있다. 정확히는 **"의존성이 그대로면 다시 계산하지 않는다"** 이다.

리렌더링이 일어나면 **컴포넌트 함수 전체가 처음부터 다시 실행된다.** `useMemo` 가 있는 줄도 실행된다. 다만 안에 넘긴 **함수를 호출할지 말지**만 갈린다.

**내부 원리**

React는 컴포넌트마다 훅 목록을 들고 있고, `useMemo` 는 거기에 `[지난 결과, 지난 의존성]` 을 저장한다.

```
1. 저장해둔 의존성 배열을 꺼낸다
2. 지금 넘어온 배열과 원소를 하나씩 비교한다 (Object.is)
3. 전부 같으면  → 저장된 값 반환. 함수 호출 안 함
   하나라도 다르면 → 함수 호출 후 결과와 의존성을 저장
```

React는 훅을 **이름이 아니라 호출 순서로** 구분한다. 그래서 조건문 안에 훅을 넣으면 안 된다. 어떤 렌더에서 건너뛰면 순서가 밀려 다른 훅의 값이 들어온다.

**참조 비교라는 점이 핵심이다.** 내용이 같아도 새 배열·객체면 다시 계산된다.

```tsx
// 매 렌더마다 새 객체 → 의존성이 항상 달라짐 → useMemo 가 무의미
const options = { size: 10 };
const result = useMemo(() => compute(options), [options]);
```

`useCallback` 이 존재하는 이유도 같다. 함수도 매번 새로 만들어진다.

**보장이 아니라 최적화다.** React는 메모리 확보 등의 이유로 캐시를 버릴 수 있다. 로직의 정확성이 캐시에 의존하면 안 된다.

**정직하게 말하면**, 일정 6건 기준으로는 지금 쓴 `useMemo` 두 개 모두 성능 이득이 거의 없다. 남겨둔 이유는 (1) 데이터가 늘면 의미가 생기고 (2) 나중에 `React.memo` 를 붙일 때 참조가 안정돼야 하기 때문이다. "일단 붙이고 보는" 습관은 권하지 않는다.

### 3-3. `useState` 의 지연 초기화

같은 원리가 초기값에도 있다.

```tsx
useState(new Date())        // 매 렌더마다 실행되고 첫 값만 쓰임
useState(() => new Date())  // 첫 렌더에서만 실행됨
```

### 3-4. 날짜 계산은 경계에서 깨진다

"다음 정각"을 구하는 로직을 만들면서 경계값을 따로 검증했다.

```js
at.setHours(now.getHours() + 1, 0, 0, 0)
```

| 입력 | 결과 |
|---|---|
| 13:46 | 14:00 |
| 14:00 (정각) | 15:00 |
| 23:30 | **다음날 00:00** |
| 8/31 23:10 | **9/1 00:00** |
| 12/31 23:05 | **2027/1/1 00:00** |

`setHours(24, ...)` 로 넘어가도 JS `Date` 가 알아서 날짜·달·해를 넘겨준다. 다만 **직접 확인하기 전에는 믿지 않는 게 좋다.** 스크립트로 7건을 돌려봤다.

## 4. 만든 것

```
components/layouts/
├─ AppShell.tsx                  헤더 + 사이드메뉴 + 본문 배치
├─ Header.tsx
├─ SideMenu.tsx                  카테고리 목록
└─ Calendar/
   ├─ ScheduleCalendar.tsx       월 그리드 + 달 이동
   └─ ScheduleCalendarCell.tsx   하루 칸
```

**`AppShell` 은 본문을 `children` 으로 받는다.** 달력을 넣든 목록을 넣든 이 파일은 바뀌지 않는다. 달력이 데이터를 필요로 하는데 그 데이터를 들고 있는 쪽은 `App` 이라, 달력도 `App` 이 그려서 넘긴다.

**달력**은 필요한 주 수만 그린다(4~6줄). 날짜별 일정은 `Map` 으로 미리 묶어둔다 — 칸마다 전체를 훑으면 `날짜 수 × 일정 수` 만큼 비교하게 된다.

**폼**은 목록 상단의 `+` 버튼으로 여닫는다.

- 시작 시각 기본값은 **다음 정각**
- 종료 시각 칸은 표시 여부를 고를 수 있고 기본은 꺼짐
- **저장 실패 시 폼이 닫히거나 입력이 지워지지 않는다** — `onSubmit` 이 성공 여부를 돌려준다

마지막 항목은 처음에 놓쳤던 부분이다. 실패했는데 입력이 사라지면 처음부터 다시 써야 한다.
